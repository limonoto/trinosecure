# 05 — Database Schema

The application database is the **backup / persist + audit layer** (Priority 2). The config
**files** Trino reads are the source of truth (Priority 1). On a confirmed import, the DB is
updated to match the files.

> This is the **planned initial** schema. It will be implemented with Prisma migrations in
> Phase 0/1. Update this file whenever the schema changes (and never use `db push` for schema
> changes — use migrations).

## Entities

### `TrinoEnvironment`
A managed Trino cluster.

| Field | Type | Notes |
|-------|------|-------|
| id | string (cuid) | PK |
| name | string | unique, e.g. "prod", "staging" |
| deliveryMode | enum `HTTP` \| `FILE` | how config reaches Trino (see [02](02-architecture.md)) |
| configTarget | string | HTTP endpoint or filesystem path base |
| refreshPeriod | string? | e.g. `1s`, mirrors Trino's `security.refresh-period` |
| createdAt / updatedAt | datetime | |

## Relationships (overview)

```
TrinoEnvironment 1───* AppGroup 1───* AppGroupMember
TrinoEnvironment 1───* ConfigArtifact 1───* ConfigVersion
(any actor action) ───* AuditLog
```

## Notes

- **Users are not owned here.** Identity comes from Keycloak; we store `username` strings as
  references (and the actor on audit/version records). An optional cached `AppUser` table may be
  added later if needed for display.
- **Files remain authoritative.** `ConfigVersion.content` is the app's copy/backup; publishing
  (Mode A/B) is what makes it real for Trino.
- All schema changes via Prisma migrations with descriptive names.
- **Prisma 7 specifics:** client generated by the `prisma-client` generator to
  `src/generated/prisma` (gitignored; `postinstall` regenerates); runtime connects via the
  `@prisma/adapter-pg` driver adapter (`src/lib/db.ts`); the Migrate URL lives in
  `prisma.config.ts` (Prisma 7 disallows `url` in the schema datasource).
- The "active" version of an artifact is `ConfigVersion.isActive = true` (rollback flips it),
  rather than a `currentVersionId` pointer.

## v2 additions (NİZAM rewrite, migration `…_nizam_v2_…`)

The schema was extended for the full NİZAM scope (see [07-roadmap.md](07-roadmap.md)). New enums:
`AppRole` (VIEWER/CONFIG_EDITOR/PLATFORM_ADMIN), `TrinoNodeType`, `PasswordEncoding` (BCRYPT/PBKDF2),
`AlertKind`, `AlertComparator`, `AlertStatus`. `ConfigArtifactType` gained `RESOURCE_GROUPS_JSON` +
`CATALOG_PROPERTIES`; `AuditAction` gained `DEPLOY` + `RESTART`.

| Model | Purpose (requirement) |
|-------|-----------------------|
| `AppUserRole` | Role per Keycloak username; null `environmentId` = global. Optional `scopeConfigTypes` / `scopeResourceGroups` arrays restrict a CONFIG_EDITOR (3.1/3.2). |
| `TrinoNode` | Cluster node inventory — drift checks (5.3), node metrics (6.3), "user on all nodes?" (2.3). |
| `PasswordEntry` | `password.db` entry — `passwordHash` + `encoding`, never plaintext (2.1). |
| `CatalogConfig` | Catalog connector config (`connector` + `properties` JSON) (2.1). |
| `QueryStat` | Per-query stats from `/v1/query` — error analytics (6.2) + performance (6.4); upserted by `(environmentId, queryId)`. |
| `NodeMetric` | Per-node point-in-time metrics from `/v1/node` (6.3). |
| `ClusterMetric` | Cluster-wide health from `/v1/cluster` (6.3.1). |
| `ErrorBucket` | Pre-aggregated error counts per time bucket; `username`/`resourceGroup` default `""` so the unique upsert key works (6.2.2). |
| `AlertRule` / `AlertEvent` | Static/dynamic alert rules + fired events (6.6). |

All carry `environmentId` and cascade with their environment, keeping installations independent.

## v3 additions (gap-closure, migration `…_add_password_db_artifact_type`)

- **`ConfigArtifactType.PASSWORD_DB`** — `password.db` is now a versioned artifact. Every password
  mutation snapshots the rendered file as a new `ConfigVersion` (history + rollback, 4.1); rollback
  re-materializes `PasswordEntry` rows from the snapshot (`src/lib/passwords/service.ts`). Catalogs
  are versioned the same way under `CATALOG_PROPERTIES`, name `<catalog>.properties`
  (`src/lib/catalogs/service.ts`).
- **`AuditLog.before/after` now carry real content.** `ConfigArtifact` saves/rollbacks store the
  previous/next file content (not just the version number) so the audit drawer shows what actually
  changed (3.3).
- **`AppUserRole.scopeConfigTypes` / `scopeResourceGroups` are now enforced** in
  `src/lib/authz.ts` (`getAccess`, `ensureConfigWrite`, `ensureResourceGroupWrite`) — a scoped
  CONFIG_EDITOR can only edit the listed files / resource groups (3.2).
- **`NodeMetric` is now populated per node** (coordinator + each worker): `cpuPercent` / `heap*` /
  `nonHeapBytes` from each node's `/v1/status`, and `activeTasks` / `failedTasks` from `/v1/task`
  (when reachable) or the `/v1/node` failure detector (6.3.2).

## v4 additions (properties management, migration `…_add_properties_artifact_types`)

- **`ConfigArtifactType.RESOURCE_GROUPS_PROPERTIES`** — `resource-groups.properties` is now a
  versioned artifact. Managed at `/properties` → "resource-groups.properties" tab; supports both
  `file` mode (points to the JSON file) and `db` mode (database-backed HA with JDBC URL, user,
  password, environment name, and refresh interval).
- **`ConfigArtifactType.GROUP_PROVIDER_PROPERTIES`** — `group-provider.properties` is now a
  versioned artifact. Managed at `/properties` → "group-provider.properties" tab; supports `file`
  and `ldap` group-provider names with their respective field sets.
- Both new types flow through the deploy pipeline (`buildFileMap`, `destinationFor`,
  `verifyConsistency`, `generateAnsibleArtifacts`, `importConfigFromTrino`) exactly like the
  existing `ACCESS_CONTROL_PROPERTIES` and `AUTH_PROPERTIES` types.
